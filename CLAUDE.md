# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Single-source DMR codeplug management for an AnyTone radio fleet (AT-D878UV II,
AT-D578UV II, AT-D168UV) using [qdmr](https://dm3mat.darc.de/qdmr/)'s extensible
YAML codeplug format. One shared `base.yaml` defines everything common (radio
IDs, contacts, group lists, channels, zones, scan lists, the APRS system);
small per-radio `overlays/*.yaml` carry only the differences (mainly
programmable-button assignments). A `justfile` drives merge → verify → write
via `yq` and `dmrconf`. There is no application code here — this is
config/data plus a build pipeline.

## Commands

```bash
just --list                  # list public recipes (the `_resolve` helper is private, hidden from this list)

just build 878                # merge base + overlay, verify against device limits (no hardware I/O)
just flash 878                 # build, then write to the connected radio
just readback 878              # read the codeplug back off the radio
just verify-roundtrip 878      # flash -> wait for the radio to settle -> readback -> semantic diff (needs dyff)
just detect                    # confirm what radio/port is connected
just clean                     # rm -rf build/
```

`878`, `168`, `578` are aliases for the real dmrconf radio identifiers
`d878uv2`, `d168uv`, `d578uv2` (resolved in the private `_resolve` recipe);
fully-qualified names work everywhere too. `flash`/`readback`/`detect` all
accept an optional trailing serial-device argument (`just flash 878
cu.usbmodem14201`), defaulting to `$DMRCONF_DEVICE` or dmrconf's auto-detect
if unset. **Pass the bare filename under `/dev/`, not the full path** —
`dmrconf -D /dev/cu.usbmodem14201` fails to find the device, while `-D
cu.usbmodem14201` works; confirmed on real hardware across all three radios.
`verify-roundtrip` also accepts an optional delay-in-seconds argument
after the device, defaulting to `$DMRCONF_ROUNDTRIP_DELAY` or 8s — in
practice this has repeatedly been too short (see Known issues).

Prerequisites: `yq` (mikefarah, v4+), `just`, `qdmr`/`dmrconf`, optionally
`dyff` for round-trip diffs. macOS: `brew install yq just dyff qdmr` — the
`qdmr` Homebrew formula installs both the `qdmr` and `dmrconf` binaries.

**Which dmrconf runs:** every recipe uses the justfile's `dmrconf`
variable, which prefers a locally built, patched binary at
`~/dev/qdmr-upstream/build/cli/dmrconf` (D168UV key-function fixes, see
`EXPERIMENTS.md` / qdmr#1018) and falls back to `dmrconf` on `PATH` if it
isn't there. Override with `DMRCONF=/path/to/dmrconf`; `just --evaluate
dmrconf` shows the one in use. Remove the local build once a qdmr release
includes the fix.

There are no tests, lint, or CI in this repo — the only "test" is
`dmrconf verify` (run automatically by `just build`) and, optionally,
`just verify-roundtrip` against real hardware.

## Architecture

- **`base.yaml`** — the source of truth for everything shared. Routine edits
  (adding a repeater, a talk group, a zone) go here.
- **`overlays/{d878uv2,d168uv,d578uv2}.yaml`** — per-radio deltas only,
  primarily `settings.anytone.keySettings` (physical button mappings).
- **`justfile`** — `build` runs `yq eval-all 'select(fileIndex==0) *
  select(fileIndex==1)' base.yaml overlays/<radio>.yaml > build/<radio>.yaml`,
  then `dmrconf verify --radio=<radio>`. `flash`/`readback` add `dmrconf
  write`/`read`. All hardware-facing recipes share serial-device resolution
  and `-D` flag assembly.
- **`build/`** — gitignored, fully disposable, regenerated by `just build`.
  Never hand-edit.
- **Every codeplug file uses `.yaml`, not `.yml`**, project-wide. This isn't
  cosmetic: `dmrconf read` fails to auto-detect output format from a `.yml`
  extension ("Cannot determine file output type"), even though `verify`/
  `write` handle both fine. `readback` also always passes `--yaml` explicitly
  as a second line of defense.

### Merge semantics (important gotcha)

`yq`'s `*` operator deep-merges maps but **replaces arrays/lists wholesale**
— it cannot merge list items by `id`. Practically:

- Overlays are safe as long as they only touch settings *maps*.
- The one exception already in play: `d878uv2.yaml` and `d578uv2.yaml` each
  carry a full, duplicated `positioning:` block, because AnyTone radios only
  support one FM APRS profile and an overlay's partial `positioning:` list
  would otherwise silently wipe out `base.yaml`'s entry for that radio's
  build. Keep these in sync with `base.yaml` by hand unless a radio should
  deliberately beacon differently.
- Simple per-radio rewrites of list items go in the `fixup` yq expression
  in the justfile's `build` recipe (applied after the merge). Currently
  only the D168UV uses it: its channels have no `Max` power, so `Max` is
  rewritten to `High` for that build.
- The first time a per-radio **channel** difference is needed, the merge
  step will need to switch to an id-aware YAML merger — naive `yq *` will
  not do the right thing for a partial channel list.

### Zones and scan lists

Each zone (except APRS) has a matching scan list with the same channels,
and every zoned channel points at its zone's list via `scanListRef:` (the
YAML key is `scanListRef`, not `scanList` — an unknown key is silently
ignored). AnyTone scan lists cap at **50 channels** and `dmrconf verify`
does *not* check this, so large areas are split into multiple zones
(Santa Clara 1/2/Dig). Deliberate mismatches: Contra Costa's scan list
omits the `ch120` divider, and Alameda's (52-channel zone) omits `ch180`/
`ch181` to stay at 50. When adding a channel to a zone, add it to the
matching scan list and give it `scanListRef` too.

### AnyTone key-function model

`settings.anytone.keySettings` in each overlay maps physical buttons to
qdmr/AnyTone function names. The canonical function enum and field
semantics are documented at qdmr manual
[ch04s04](https://static.dm3mat.de/qdmr/manual/ch04s04.html) ("Settings
extension" → "Keypad settings"). The manual's list is incomplete — the authoritative enum is
`AnytoneKeySettingsExtension::KeyFunction` in
`~/dev/qdmr-upstream/lib/anytone_settingsextension.hh` (e.g. `ZoneUp`,
`ZoneDown`, `Menu`, `Exit`, used on the 578, are valid there but missing
from ch04s04). Physical layout differs by radio:

- **D168UV** (HT): only PF1/PF2 exist (`funcKeyA`/`funcKeyB`). Everything
  else is omitted from the overlay and inherits `Off` from `base.yaml`.
- **D878UV II** (HT): P1/P2 (`funcKey1`/`funcKey2`), PF1/PF2/PF3
  (`funcKeyA`/`B`/`C`; PF3 is the orange top key). `funcKey3-6`, `funcKeyD`,
  and the knob don't exist on this radio.
- **D578UV II** (mobile): P1-P6 (`funcKey1-6`) on the control head, plus
  PF1/PF2/PF3/D and a push-knob on the hand mic (`funcKeyA-D`,
  `funcKnob`).

Overlays are comment-annotated with physical key labels and a one-line
description of each assigned function — preserve that convention when
editing keySettings.

### Boot channel defaults

`settings.boot` (the generic, non-AnyTone-specific `BootSettings` class —
same one that holds `display`/`message1`/`message2`/`passwordEnabled`/
`password`/`allowFactoryReset`) also carries `defaultChannel`, `zoneA`,
`channelA`, `zoneB`, `channelB`: whether the radio jumps to a specific
channel on each VFO at power-on, and which zone/channel to use. This is
**separate** from `settings.anytone.bootSettings`, which only holds
`priorityZoneA`/`priorityZoneB`/`gpsCheck` and has no channel fields —
don't confuse the two when editing boot behavior. Currently both VFOs
default into zone2 ("San Francisco"): VFO A → `ch13` (Sutro VHF), VFO B →
`ch16` (Sutro DMR NORCAL). `channelA`/`channelB` must be members of
`zoneA`/`zoneB`'s channel list.

## Known issues / open items

- `base.yaml`'s `positioning[0].aprs.source` is `SAG-7`, which doesn't match
  the operator's callsign (KR6A). `d578uv2.yaml`'s duplicated positioning
  block already uses `KR6A-1` instead — the 878's copy (and `base.yaml`)
  still need a deliberate `KR6A-N` SSID before either radio transmits real
  APRS beacons.
- Zone up/down is bound redundantly on the 578 across four buttons (P3, P6,
  PF2, PF3) — confirm this is intentional rather than leftover iteration.
- `test.yaml` and `files.zip` at the repo root are unexplained / possibly
  stray scratch artifacts — confirm whether they're still needed.
- `build/*.yml` (old pre-rename extension) couldn't be removed in one
  session — deletion failed with "Operation not permitted" (possibly a
  Dropbox sync lock). Harmless; `just build` writes fresh `.yaml` output
  alongside them regardless.
- `overlays/578-key-mapping-reference.yaml` is documentation-only (not
  consumed by the build), mirroring `d578uv2.yaml`'s keySettings with fuller
  prose commentary. Keep it in sync if the overlay changes, or remove it
  now that the overlay itself carries inline comments.
- `just verify-roundtrip 878` shows `channels.*.anytone.throughMode`
  going from `true` (written) to `false` on 7 DMR channels. This is **not
  the radio**: a purely local `dmrconf encode` → `decode` of
  `build/d878uv2.yaml` (no hardware) shows the same flip, so qdmr's 878
  codec drops the value (either never encodes it or decodes it wrong — not
  yet traced). qdmr's own docs for the field just say "if true, the
  through mode is enabled. Whatever that means." Low priority unless a
  bench test turns up an audible effect.
- The radio's USB serial port frequently takes **longer than the default
  8s `roundtrip_delay`** to reboot and re-enumerate after a write —
  confirmed on all three radio models. `readback` (inside
  `verify-roundtrip` or standalone) fails with "device ... not found" if
  it runs before the port comes back; the fix so far has just been to
  retry after a few more seconds, or pass a longer delay
  (`DMRCONF_ROUNDTRIP_DELAY`/trailing arg). Worth considering a longer
  default or built-in retry logic in the `readback`/`verify-roundtrip`
  recipes.
- On the D168UV, `settings.anytone.keySettings.funcKeyBLong` (`SubChannel`
  in both `base.yaml` and `overlays/d168uv.yaml`) did not stick via
  `just flash`/`dmrconf write` — a round-trip read back showed `Off`.
  Setting the same function manually through the radio's front-panel menu
  *did* stick and read back correctly. **Root cause confirmed (2026-10-27)
  as libdmrconf bugs** — `funcKeyBVeryLong` is written into PF2 long's
  byte, long/very-long functions above `Zone` are encoded with the wrong
  table, and short keys use the D878 table (wrong at least for Squelch).
  Full evidence and radio memory map in `EXPERIMENTS.md` (qdmr#1018).
  Fixed in the locally built dmrconf the justfile now uses (verified on
  the radio, F2/F3); not yet in a qdmr release.
- Relatedly: when manually reprogramming keys via the front panel to work
  around the issue above, it's easy to introduce an *unintended* extra
  binding while navigating the menu — one such session left PF1's
  very-long-press (`funcKeyAVeryLong`) set to `SubChannel`, which isn't in
  the codeplug at all. Always `readback` + `dyff` against
  `build/<radio>.yaml` after manual front-panel edits, before the next
  `flash` silently overwrites (or fails to overwrite) the drift.
- The D168UV build emits 98 `Property 'groupList' must refer to an
  instances of RXGroupList` warnings — one per DMR channel, since none has
  an RX group list. **Harmless:** qdmr's `d168uv_limits.cc` declares
  `groupList` as non-nullable (`RadioLimitObjRef(RXGroupList::staticMetaObject,
  false)`), while `d878uv2_limits.cc` allows null (`true`); the D168UV
  inherits the shared AnyTone channel encoder, which writes a null list as
  `0xff` ("None"), and real 168 readbacks (`2026-08-10-d168.yaml`,
  `build/d168uv-readback.yaml`) show all DMR channels with no group list,
  so the radio accepts it. Don't "fix" it by assigning `grp1` — it holds
  only the `cont1` placeholder (TG 1) and would add TG 1 to every
  channel's receive list. Planned fix: flip that `false` to `true` upstream,
  deferred until qdmr#1018 is merged.
- qdmr maps 1-10 YAML levels to the radio's smaller ranges with
  round-down integer math, and decode isn't the inverse of encode
  (`Range::mapTo` in qdmr's `lib/codeplug.hh`). Mic gains (0-4 on the
  radio, shown as 1-5) round-trip cleanly only on odd values 1/3/5/7/9 —
  see the comment in `base.yaml`. `maxSpeakerVolume` (0-8) reads back one
  lower for every value except 1 (e.g. 7 → 6), so roundtrip dyffs always
  show it; the radio holds the written value. Never copy a readback's
  volume back into the codeplug — it would drop a step each cycle. The
  radio's "Auto" mic gain isn't representable in qdmr. Candidate upstream
  fix (round-to-nearest), not yet filed.
- `settings.gpsSettings.timeZone` is `UTC-07:00` (Pacific Daylight, correct
  as of mid-2026). AnyTone radios don't auto-adjust for DST, so this needs
  a manual flip to `UTC-08:00` around the fall/spring clock change to stay
  accurate.
